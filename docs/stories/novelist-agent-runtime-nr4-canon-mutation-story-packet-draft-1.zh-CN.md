## 1. 交付目标与非目标

用户在正常聊天中表达确定的角色、世界、素材、剧情或大纲决定时，AI 自主选择内置写作方法、读取相关资料、请求安全创建或更新 Markdown；Host 执行并提供可信的“已保存 / 待确认 / 未保存”结果、Diff 和 Undo。用户不需要说 Skill 名称、选择工具或创建 Anchor。

这不是“每次写入都弹确认”的产品。用户明确决定、纠正和任务可以自动落盘；AI 自己的建议、猜测和备选方案不能静默成为 Canon。来源有歧义、目标有冲突或变化具破坏性时才等待选择。

本阶段不交付章节写入/提交、EPUB、图像生成、任意文件操作、删除/重命名/实体合并工具、后台批量维护、通用多任务 Agent、自动 Provider 重试、云同步或外部 Skill Runtime。NR-5～NR-7 未形成 Packet、未获实施授权。不恢复独立 Pre-NR-4 计划，也不重开 NR-G4。

## 3. 冻结候选合同

以下是 Draft 1 提案，待产品决定后成为实施约束；不是对当前运行能力的描述。

### 3.1 Skill 与 Tool 分工

- 九项 Novelist 能力继续是编译期嵌入的方法、模板和参考资料。模型按语义选用；不是九个独立可执行程序，也不要求供应商理解名为“Skill”的特殊协议。
- `novelist.read_context` 继续负责读取选定能力及允许范围内 Canon。新增读取回执只用于绑定已读取的目标版本，不赋予写权限。
- 新增一个内部 `novelist.propose_change` v1；Provider wire 名为 `novelist_propose_change`。现有只读 wire 名仍为 `novelist_read_context`。映射唯一且可逆，不接受别名猜测。
- 新工具提交类型化变更集。Host 根据已声明来源、风险和客观校验，自动提交、保存待确认草稿或拒绝；工具调用成功不必然代表文件已保存。
- 确认、放弃、查看 Diff、Undo 是当前 Turn 内的本地类型化操作，不另发模型请求。自然语言确认也可以进入下一 Turn，模型重新提交并引用该用户决定。
- 修改应用自有 NR-4 投影，不改变上游 `novelist 0.2.0` 来源标识；另外冻结投影修订、清单及全部 Hash。破损 Pack 原子撤下目录与工具，普通聊天继续。不得读外部缓存或执行 Python/Shell。

### 3.2 目标与 Mutation

| 类型      | 唯一可写目录  | 能力方法来源                                 |
| --------- | ------------- | -------------------------------------------- |
| character | `characters/` | create-character                             |
| world     | `world/`      | create-setting                               |
| material  | `materials/`  | create-material                              |
| plot      | `plot/`       | create-plot                                  |
| outline   | `outlines/`   | novel-story-telling 中的大纲方法，非章节写入 |

仅允许符合相应模板的 Markdown；`chapters/`、`macguffins/`、`style/`、资产、`project.md`、元数据及 `.novelgainker/**` 均不是该工具的 Canon 写目标。状态库只能由 Host 内部管理。

当前内置包没有 outline 模板；`novel-story-telling` 仅列有 chapter 模板。NR-401 须定义应用自有 outline 类型、身份及必需 frontmatter，NR-403 将其模板作为新增投影资源纳入清单/Hash；不得直接把章节模板改目录后当大纲，也不把新资源冒称上游原件。

请求包含固定版本、能力 ID、来源类别及引用、风险分类、操作列表；每项包含实体类型、目标句柄或新实体请求、完整候选 Markdown、预期版本及读取回执。工程/Session/Turn 从运行时绑定，不信任模型自行指定。限制未知字段、操作数、实际序列化字节和类型组合。

各操作分别绑定其能力 ID 和本 Turn 已加载方法的回执；跨类型关联更新逐项验证上表权限，不能用一个能力的只读范围自动获得其他类型写权限。来源 ID/Hash 由 Host 向模型提供有界引用，不要求模型猜测消息 ID。

- `create`：Host 生成安全文件名和新实体标识，预期不存在；碰到同名/同标识候选不偷偷改成覆盖。
- `update`：引用读取结果中的不透明目标句柄、完整读取回执和 `expectedSourceHash`，保留既有实体身份。不允许仅据路径或搜索摘要覆盖文件。
- `upsert`：表示模型的语义维护意图，Host 必须先解析为确定的 create 或 update，再执行对应前置条件；不是无条件覆盖 API。
- 相同名字不足以判定相同实体。一个以上匹配、缺失标识或矛盾映射进入待确认；Host 不猜合并规则。
- 修改前校验 UTF-8、换行及模板/frontmatter，并由 Host 比较规范化后的实际字节生成 Diff。不得接受模型宣称的空 Diff 作为事实。
- AI 应最小改动，保留无关段落及属性；Host 检查结构性丢失并升级风险，不能声称能机械证明语义等价。内容层面的大范围重写、批量删段和未知字段丢失不得走自动提交；这不禁止用完整候选字节承载小幅修改。

### 3.3 来源、自动执行与确认

| 来源/情况                            | 处理及证据要求                                                                              |
| ------------------------------------ | ------------------------------------------------------------------------------------------- |
| 用户明确决定、纠正、任务             | 可自动提交；引用本工程 Session 内已持久化的用户消息与其 Hash，不能用 assistant 消息充当授权 |
| 用户接受 AI 建议                     | 接受消息是用户来源，同时引用实际采纳的建议；不能仅以旧建议或含混“好”自动扩大范围            |
| AI 构思、假设、备选方案              | 留在对话，不自动写入；即使来源引用存在，也不转成用户决定                                    |
| 正式章节中的无歧义事实               | 必须有 Host 可核对的正式提交来源，而不只是文件存在或读取 Hash；见下述阶段衔接决定           |
| 语义冲突、歧义目标、范围不明、大覆盖 | 保存待确认 Diff；具体目标和内容未确定时只询问，不形成可直接提交的变更                       |
| 删除、合并、重命名请求               | 说明影响并询问；本阶段无对应通用执行器，不以“已确认”绕过 create/update 白名单               |

Host 只证明来源存在、角色/工程/Session 正确、版本一致及操作边界成立；不能证明 AI 正确理解“用户已决定”。模型的来源分类和冲突判断是语义风险，不是安全证明。不得通过 Host 关键词 Router 修补，也不得声称凭消息 ID 已彻底防止建议误落盘。NR-406 必须分别记录机械反例覆盖与未验证的真实模型语义质量。

**章节来源衔接提案（需产品决定）**：当前尚无正式章节 Commit 合同，NR-501/502 才负责建立它。NR-4 保留 `chapter_commit` 类型及严格拒绝/待确认分支，但没有可验证提交回执时不自动执行此分支。用户明确要求“以当前章节这项事实更新角色”可作为用户任务来源正常落盘。NR-G5 如接受该分期，应明确“用户来源已交付；章节独立自动来源等待 NR-5”，不能把合成回执测试算作生产支持。若要求 NR-G5 即完整交付章节自动来源，须先修订此 Packet，补齐正式来源识别合同，不能直接宣称通过。

### 3.4 最小 Agent Loop 与预算

默认流程为 `自然聊天 → 按需读取（最多两次）→ 最多一个变更集 → 自然回复`。每轮仅一个工具调用，严格顺序；允许零工具、一次读取即完成、读取后不写入。提交变更或获得待确认结果后，余下回复不再提供工具。超出读取预算则说明缺少的资料，不靠猜测写入；下一个用户 Turn 可以继续。

| 项目                                           |        NR-4 Draft 1 上限 |
| ---------------------------------------------- | -----------------------: |
| Agent 请求 / Compactor 请求 / 总 HTTP attempts |                4 / 1 / 5 |
| 每次 Agent / Compactor 请求输出                |     4,096 / 1,024 tokens |
| 累计请求输出                                   |            17,408 tokens |
| 只读执行 / 变更集执行                          |                    2 / 1 |
| 变更集内不同目标                               |                        4 |
| 单目标完整原文及候选各自                       |                    8 KiB |
| 变更集候选正文合计                             |                    8 KiB |
| Tool Definitions / Arguments / Result          |         24 / 16 / 24 KiB |
| 累计 Provider Continuation                     |                  160 KiB |
| Agent Loop Reserve / 完整 Provider Body        |            192 / 256 KiB |
| 单工具 Deadline / 取消确认                     | 30 seconds / ≤ 2 seconds |

这是小型资料维护起步范围，不是 4 MiB 手工编辑上限的替代。超过 AI 写入范围的文件仍可手工编辑/只读处理；不得悄悄截断后提交。正文上限不是保证所有输入都能通过：JSON 转义、工具定义、来源和双 Provider 包装按实际序列化计费，完整请求、单消息及 Continuation 上限均独立生效。

必须在变更发生前预留有界结果和最终回复请求空间；若不够就零写入返回受控失败，不在提交后才发现下一请求超限。每次执行前消费预算，重复 Tool ID 不再次执行。不得把额度增加变成自动重试、后台任务或并行工具。普通聊天不因为新上限增加无关调用。

### 3.5 写入、恢复、幂等与 Undo

1. 解析请求并校验来源、能力和目标；获取完整目标版本，校验每项预期 Hash/不存在条件及只读回执完整性。
2. 检查编辑器未保存缓冲区、项目身份、路径包含关系、重解析点/符号链接及跨进程 Writer Lease。对同一文件的手动保存和 AI 保存共用协调；不得在 Provider 等待期间持有写锁。
3. 写入任何 Canon 前，持久化规范化候选、字节复制的 before-image、afterHash、操作顺序、来源摘要和变更 ID。不能把可随原文件就地编辑而变化的 hard link 当作不可变 Undo 快照。
4. 事务执行期间持有项目写租约；各文件替换前重新校验，单文件采用现有安全原子写入内核。预检全部目标不代表后续可跳过 Hash/路径检查。
5. 全部目标成功后持久化提交标记和回执，再报告已保存。提交结果和 Task 投影允许可恢复地补齐，但不能 best-effort 丢弃决定“是否已保存”的证据。
6. 提交标记前失败/取消：只在当前文件仍等于本次 afterHash 时按逆序恢复。遇到外部改动不覆盖，标记 `recovery_required`、保留全部证据并暂停受影响工程的进一步写入；聊天和只读可继续。
7. 标记后 Provider 失败、关窗或 Task 持久化失败不能否认已保存。重开先核对事务真相再恢复 Task；不把所有遗留 running 写任务直接当作零副作用取消。
8. Undo 是本地、显式、按变更集的逆事务。所有目标须仍匹配该变更 afterHash；任一不匹配则整个 Undo 预检失败、保留文件。撤销创建只移除本次创建且内容未变的文件；撤销更新恢复精确 before-image。Undo 本身也须恢复和幂等。

多文件只承诺应用协调范围内的事务一致性与可恢复部分失败；不声称 Windows 对任意外部编辑器提供多文件原子可见性。应用内读操作须识别事务 revision：进行中不把部分文件作为一个完整已提交快照返回，恢复未决时显式标注不一致；不能仅有写锁就宣称读隔离。外部编辑产生的无法回滚状态要如实显示，不能宣称“所有失败都零变化”。

幂等键由 Host 绑定工程、Session、Turn、Tool Call ID 和规范化请求摘要；同键同摘要返回原回执，异摘要拒绝。确认/Undo 以变更 ID + revision 做 CAS，双击、旧页面和崩溃重开不得重复执行。新一轮语义相同请求不保证仅靠 ID 去重，必须重新读 Canon，空 Diff 返回 `no_change`。

### 3.6 独立变更记录与状态

新增 Host 私有 `.novelgainker/changes/` 有界、版本化变更库，用于规范化候选、不可变 before/after 字节快照和回执。它不是 Canon，不参与索引/出版，不存原始 Provider 响应、原始 Tool JSON、隐藏提示或 Continuation；Task 仍只存有界状态和摘要。这是本 Packet 明确提出的本地草稿/Undo 存储，不伪装成已有 Task 能力。

初始配额提案：单工程 64 MiB、最多 100 条有内容的变更记录、其中待确认最多 10 条；先预留本次事务及 Undo 所需容量，失败则不写 Canon。不得为腾空间静默删除仍可撤销的内容。需用户明确清理记录时告知相应 Undo 丢失；不删除 Canon。状态库丢失不损害已提交 Canon，但不能重建已丢失的历史 Undo。

变更生命周期为 `prepared → pending_confirmation / applying → committed`，另有 `no_change / rejected / cancelled / recovery_required / undone`；Task 的 `succeeded` 只说明工具返回了有效结果，不替代变更状态。未完成危险恢复不能靠清空 App State 解决。

待确认 Diff 不持有写锁。确认前重验目标、Hash、用户编辑 revision 和来源；过期不能以“用户点过确认”为由强制覆盖。用户放弃仅丢弃待确认候选，不修改 Canon。范围尚不明确的候选不可确认。

### 3.7 UI、IPC、聊天与关闭

- 保持三栏；在当前 Turn 内提供简短 Host 结果及“查看更改 / 撤销”，待确认显示“确认保存 / 放弃”。Diff 使用现有工作区可承载的局部查看区，不新增 Task Center、第四栏或 Skill 卡。
- 显示确定的事实：“已保存 1 项资料”“待你确认，尚未保存”“保存失败，原文件未变”或“部分写入待恢复”；“原文件未变”只有查证零变化才可使用。
- 模型说“调用了”“已完成”不能代替 Host 证据。成功回执包含变更 ID、revision、受控相对目标、前后 Hash 和结果；不向对话正文输出协议 JSON。
- 所有非空回复保留。工具失败但模型自然回复正常结束，不改成“本次回复未生成”；真正的 Provider 中断可按现有规则追加未完成提示，不能抹除此前内容。
- 类型化本地边界至少涵盖变更详情读取、确认/放弃、Undo、编辑缓冲区 dirty/revision 登记；入参限工程/Session/文件句柄、变更 ID、revision、dirty 布尔值和封闭动作，不接受任意文件路径/写入正文。注册、权限、Handler 与生产客户端同改同测。
- 关闭窗口仍只由未保存手工 Markdown 触发“保存 / 放弃 / 取消”。待确认 AI 草稿不新增关窗阻断；正式关闭立即取消 Turn 并退出，不等待事务/Provider。事务必须依靠持久恢复，而不是强行延长关窗。

## 4. Story 分解与可验收交付

### NR-401 — Canon Mutation 与来源合同

**用户价值**：确定的写作决定能表达为受约束的文件操作，而非任意工具参数。

交付：类型/目录矩阵；工具 v1 请求结果；目标/读取/来源回执；变更状态与稳定错误枚举；Draft 1 预算；变更库 schema 和 IPC 合同。先明确能力/目录授权，不开放章节。

验收：

1. 五种类型的 create/update/upsert 可解析；未知类型/路径、跨工程/Session 引用、伪造角色及篡改 Hash 拒绝。
2. 搜索片段、未读完的大文件或不匹配完整回执不能更新；不存在目标只能按 create 前置条件提交。
3. 自动/待确认/拒绝/无变化/待恢复可类型化区分，不将 Task 成功等同保存。
4. JSON 转义、重复目标、4/5 项边界、字节上限和双 Provider 完整请求有反例测试；缺失安全字段不得自动补值。

涉及：`canon_context.rs`、`tool_runtime.rs`、`provider_core.rs`、新 Canon Change 合同模块及架构文档。

### NR-402 — Canon Apply/Recovery 挂载

**用户价值**：AI 保存走与本地编辑同等严格、并可恢复的 Host 写入路径。

交付：仅对五类目标的生产 Executor；不可变快照；变更库配额；跨进程锁；持久事务/回执；成功后 Canon Tree 刷新。

验收：

1. 合成人物新建、已有设定更新真正修改对应 Markdown，内容、元数据、Hash 和文件树一致。
2. 越界、symlink/reparse、同名碰撞、磁盘写入失败、快照/回执写入失败均不被显示为成功。
3. 多目标逐步骤故障注入验证回滚或准确 `recovery_required`；不覆盖外部编辑；before-image 不随外部就地写改变。
4. 提交标记前后崩溃、Task 落后、重复执行恢复到同一真实结果。

涉及：`canon_apply.rs`、`recovery.rs`、`coordination.rs`、`task_store.rs`、新变更存储/执行模块。不得用章节写内核存在作为对章节开放权限的理由。

### NR-403 — 语义 Upsert 与持续维护

**用户价值**：作者只需自然讨论；AI 知道先查已有资料，再维护同一个实体。

交付：NR-4 内置指令与工具描述、大纲专用模板、保留上游来源并更新投影 Hash、有界顺序循环、双 Provider 适配与严格来源/读取绑定。

验收：

1. 同核心编排的脚本化 Provider 完成“按需取方法 → 读已有角色 → 更新”及“空工程 → 新角色”。
2. 不带关键词、直接纠正已有角色、接受建议、要求只读、闲聊、含糊赞同和假设提问均纳入来源决策测试集；测试不得在 Host 加关键词分流。
3. 同名歧义不偷偷创建重复实体；关联更新同样受来源、四目标限制及全量前置条件约束。
4. 读取两次仍不足、截断工具输出、非法请求、Pack 损坏、零工具选择均可自然结束，且不猜测保存结果。
5. 多轮原生 Tool Call/Result 严格配对，累计预算真实计算；DeepSeek 可选字段兼容不得推广为补写来源/Hash。

涉及：`capability_pack.rs`、内置 Novelist resources/manifests、`conversation_runtime.rs`、双 Provider Adapter。

### NR-404 — Diff、自动执行与确认策略

**用户价值**：明确决定自动落实，不确定变化可先看影响，不用每项机械确认。

交付：四类来源策略投影、pending Diff、本地确认/放弃、Host 结果内联、手工脏缓冲登记及对话双终态。

验收：

1. 用户明确新建/纠正自动保存并可查看 Diff；AI 建议/备选不静默落盘。
2. 冲突、范围不明、脏编辑器转待确认或只询问；确认前磁盘保持不变，编辑器缓冲保留。
3. 旧 revision、确认后源文件变化、双击、放弃后再确认均不覆盖或重复执行。
4. 工具失败仍保留完整自然回复；模型无工具自述不能显示 Host 已保存。
5. 待确认不改变关窗规则；确认按钮无需 Provider；IPC 权限、Manifest、Handler 和生产客户端一致。

涉及：Turn/Task 内联投影、Markdown editor 协调、类型化 Tauri IPC、Conversation UI 测试。

### NR-405 — 冲突检测、解决与 Undo

**用户价值**：不覆盖作者新编辑，误保存可恢复，部分失败可理解、可处理。

交付：Hash/语义/重复实体冲突分流、Diff 重新准备流程、按变更集撤销、安全恢复入口和幂等状态映射。

验收：

1. Hash 冲突由 Host 客观拒绝；语义矛盾由 AI/用户选择，新方案需重新读版本并确认，不存在 force-overwrite 绕过。
2. 创建/更新/关联多文件均可 Undo；任一 afterHash 不符时不部分撤销；重放 Undo 返回原状态。
3. 外部修改导致回滚不能安全完成时保留 Canon、候选和快照，阻止后续写入但不阻断聊天。
4. 取消、关窗、重开分别覆盖待确认、首次替换后、提交标记后、Undo 中途；禁止“磁盘已改但 UI 显示从未保存”。
5. 配额耗尽/缺失快照明确标出 Undo 不可用；不借清理状态删除作者文件。

涉及：变更库/恢复、编辑器并发协调、变更 IPC 和内联错误说明。

### NR-406 — NR-4 事务回归与 NR-G5 技术提交

**用户价值**：以可重复证据证明自动保存与不丢稿，而不是凭模型的一句“已完成”。

交付：合成小说端到端、故障矩阵、双 Provider Loopback、离线 UI/Kernel 回归、预算/发布检查、NR-G5 Manifest 与 Report。

验收：

1. 四类来源分别留证；章节来源未开放必须如实记限制，不用 Fixture 冒充生产支持。
2. 五目录真实读写、空工程、无改动、重复实体、脏编辑器、路径逃逸、并发写、磁盘错误、重放、取消和 Undo 全覆盖。
3. 完整调用体、4 Agent + 1 Compactor 极值链与超限零副作用具备机器证据；普通聊天仍零工具零写入。
4. 自包含 Pack 和权限边界回归；不引入外部 Skill/Python、任意路径、隐藏协议持久化或凭据输出。
5. `pnpm quality` 全部通过后才能声称技术提交完成；记录版本、命令、退出码、证据路径及已知限制。NR-G5 初次技术快照保持 `nrG5Approved=false`，等产品另行批准。
