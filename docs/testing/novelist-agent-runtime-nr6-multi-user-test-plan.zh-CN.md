# NR-6 多用户试用与验收方案

日期：2026-09-05。状态：方案已补充，尚未发放版本、招募用户或执行测试。

2026-09-06执行更新：NR-501～506和NR-601～603均已通过各自全量质量，现停在NR-604试用批次确认入口。工具详情、测试包与安装/升级准备仍待实施；参见[入口检查单](../reviews/novelist-agent-runtime-nr604-entry-readiness.zh-CN.md)。本方案中的建议人数、费用和试用时间尚不是已确认批次。

依据：用户接受NR-6前三项产品行为，并明确“是直接拿去多用户测试”。本方案附属于[NR-5～NR-6 Story Packet](../stories/novelist-agent-runtime-nr5-nr6-story-packet-draft-1.zh-CN.md)，不新增Story，不引入云同步、账号体系、遥测后台或自动模型批跑。

2026-09-05补漏批准：用户接受NG-F01～NG-F05五项建议。本方案据此补充定稿版本、完整创作链、内联执行证据、32个非归档会话和安装/升级/最终版复验；均落在原Story，不意味着已发放、已实现或Gate通过。

## 1. 方式、责任与边界

- 真实验证由多位参与者在自己的Windows电脑上直接使用应用完成，不是仅产品负责人自测，也不是助手代用户调用API。
- 产品负责人负责邀请参与者、确认批次范围/费用安排、发放候选版、收集自愿提交的反馈并作Gate决定。本轮只写方案，不发送邀请或对外发布。
- 开发者负责准备可复现版本与合成测试工程、离线自动化、说明书、最小证据核对、缺陷修复和复测包。助手自评不是独立用户评测。
- 建议首批5～8位用户，包含初次使用者和有小说创作经验者；尽量让DeepSeek/OpenAI各有至少2位独立测试者。一人无需测试两个Provider。人数与时间是发放前确认的建议，不是本次已获批准的额度。
- 建议每人先用45～60分钟执行分配任务，再在3～5天内自愿自由试写；可随时退出。人数不能替代覆盖，耗时也不代表完成。
- 多用户指多位测试者各用本地工程，不是多人实时协作或共享工程。测试时仅用合成内容；不要求交出真实小说、个人资料或API Key。

## 2. 什么时候能发测试版

必须先完成NR-5和NR-G6技术证据，再完成NR-601～603各自质量门，准备好NR-604测试资料。用户已另行批准NR-G6技术通过后连续实施，不需单独人工等待。当前这些质量前置已满足，但NR-604批次与程序准备尚未完成，不能把本方案或开发机EXE当成已可发放候选版。

发放检查单：

- 固定应用版本、Git提交、构建/安装包SHA-256、支持的Windows环境、已知限制和退回上一版本的方法；检查包内无凭据和真实用户数据。
- 完整`pnpm quality`通过，记录对应提交；离线验证关闭/重开、跨会话、撤销、磁盘故障、密钥保护和重复写入反例。离线结果不冒充真实Provider结果。
- 准备独立目录的E0空工程、E1小型合成小说和E2长篇合成工程（30万字、100万字两个规模）；固定文件Hash、预期事实、矛盾位置及来源答案。提供一键可理解的打开说明，不要求参与者操作隐藏状态。
- E1示例事实：林舟是钟表修复师，不会游泳；顾遥是其姐姐；北桥在暴雨夜封闭。测试前按应用有效模板准备角色、世界、剧情、纲要及章节文件；记录各任务起始版本。不得临时套用真实稿件。
- 准备可见的工具执行/变更结果入口说明及最小脱敏证据提取方法。若现有界面不能证明一次读取，开发者须在发放准备中解决可核查证据问题，不让用户猜测“是否调用”；不开放任意日志/状态导出或新增任务中心。
- 验证反馈材料只包含批准的最小字段。模型正文和“已完成”不能替代工具派发/完成回执；截图无法证明时列unverified，不编造现有产品已有诊断功能。
- NG-F03：发放版必须提供聊天内联“查看详情”，以Host最小持久回执区分已读取/未命中/执行失败/结果未核实。详情展示操作名称、相关文件或内置方法、结果和适用的Diff/Undo；无实际读取回执不能显示“已使用方法”。用户只需展开并自愿截图；开发者核对安全标识/Hash，不要求打开隐藏日志。以已有会话DTO有界扩展为首选，数据合同及脱敏负例须先验收，不新增任务中心。
- NG-F05：完成D01/D02发放检查，准备最终D03证据适用表。旧工程夹具来自已通过Gate的旧版本合法合成数据，不是只用新版模板模拟旧工程；只在副本操作，升级不得新增v1迁移器。

## 3. 参与者须知：隐私、费用与停止

发放时用简短说明告知：这是测试版，可能出错；测试内容及必要上下文会发送给参与者选定的AI Provider，工程本身不做云同步。参与者确认后自行开始操作。

凭据由参与者通过应用安全设置配置，建议使用Provider侧有限额、可撤销的测试Key；通过Rust CredentialVault保存。禁止把共享开发者Key打进包、要求参与者贴Key或远程代读其凭据。

费用承担由负责人和参与者事先约定；每人自行设置可接受金额/时间上限，能在Provider侧设置硬上限时优先设置。应用单Turn预算保持已批准合同，不能保证用户整场测试总费封顶。费用不明时先暂停，不要求继续凑覆盖；未知用量/金额如实记未知。

不安装监控软件，不自动收集日志或上传稿件。参与者经检查后自愿提供反馈到负责人确认的既有渠道；新后台/第三方表单集成不在范围内。截图须裁去用户名、绝对路径、账号及无关内容。原始请求、密钥、内部提示、整个`.novelgainker`目录不得作为反馈附件。

发现丢稿、未授权/越界写入、重复保存、密钥暴露或假报保存，立即停止受影响版本/Provider批次，通知负责人；保留隔离测试工程副本，不覆盖、不自动清理证据。如暴露Key，由参与者自行撤销。测试结束按约定期限清理反馈副本，建议Gate裁决后30天；期限须发放前告知，且不删除用户自有文件。

## 4. 执行任务单

开始时记录测试者代号、应用版本、Windows/机器配置、Provider/model与日期，不记录姓名、Key或带秘密参数的endpoint。每项从指定基线或独立工程副本开始，不能把其他测试遗留的修改当作原始事实。

### A. 基础聊天与工具（NR-604）

| ID / 工程 | 给用户的任务或示例输入 | 预期与核对方式 |
| --- | --- | --- |
| C01 / E0 | 正常聊天：帮我想三个悬疑故事开头，暂不保存。 | 正常回复；不强制工具；无新增资料。工程空/工具不可用不应抹掉回复。 |
| C02 / E0 | 请调用当前可用的只读工具，检查当前小说工程中是否存在人物资料。即使工程为空，也必须以实际读取结果为准，不能猜测；不要创建或修改任何文件。 | 实际读取后明确无人物资料。若工具真失败，应如实说明尚不能判断，不得把失败说成空工程或成功。回执证明读取，工程无写入。 |
| C03 / E1 | 请实际读取林舟的人物资料，告诉我职业和是否会游泳，不要修改。 | 回答钟表修复师、不会游泳，来源对应文件；实际读取回执且无写入。 |
| C04 / E1 | 请读取内置人物设计方法，并结合林舟资料给三条改进建议，先不保存。 | 方法资源和资料有实际读取证据，建议可理解；仅方法名称或通用回答不证明能力包已使用，无资料修改。 |
| C05 / E1 | 也许可以把林舟改成医生，只讨论利弊，不要保存。 | 讨论建议，角色职业仍是钟表修复师；AI建议不变成正式事实。 |
| C06 / E1 | 确定将林舟的职业改成医生，请更新人物资料，其余信息不变。 | 实际提交回执、Diff及磁盘一致；只改授权内容，回复不假报保存。 |
| C07 / C06后 | 查看刚才的Diff，再撤销该次修改。 | 撤销后职业及文件Hash回到before版本；不存在额外重复变更。 |
| C08 / E1副本 | 手动编辑林舟文件暂不保存，再让AI修改同一资料。 | 手动未保存内容不被覆盖；准确提示冲突/待处理，仍可普通聊天。 |
| C09 / E1 | 先要求试写一小段“不保存”，再明确要求将指定版本保存为测试章节。 | 讨论稿不落盘；明确保存后才有对应章节/回执；重开应用仍在，内容一致。 |
| C10 / E1 | 生成中点击停止，然后再发普通消息。 | 已生成文字保留，停止状态准确；不会把已有内容换成“本次回复未生成”，可继续聊天。 |
| C11 / E1副本 | 在可控条件下中断测试网络，观察错误和允许的重试入口。 | 无后台整轮重放；零文字零Tool派发才允许显式一次重试；已有文字/工具保持结果，不能重复写。无法安全稳定复现的分支记not_run，不反复断网凑结果。 |
| C12 / E1 | 完成一次保存后关闭并重开；另测试手动未保存稿的保存/放弃/取消。 | 持久聊天/文件一致；只有未保存手动稿按既有规则阻断关闭，不因工具任务增加关闭阻断。 |

C02～C09为关键工具/授权证据项。每个拟声明支持的Provider/model组合，建议由至少2位独立用户覆盖各项；C01、C10～C12至少有1位覆盖，出现问题由另一位复测。分工完成即可，不要求每人跑完全套。网络异常的确定性故障分支仍由开发者离线注入补充，未有真实证据的分支单列限制，不宣称真实通过。

### B. 会话管理（NR-601～603回归，纳入NR-604用户任务）

| ID | 用户任务 | 预期 |
| --- | --- | --- |
| S01 | 建立“人物讨论”和“章节创作”两段聊天，分别命名、切换、重开。 | 历史独立；人物资料共享最新版本；私有聊天事实不凭空串到另一会话。 |
| S02 | 生成中切换会话，再尝试发起第二次生成。 | 原任务不串到新会话；一个工程不出现两个同时生成任务，停止对象准确。 |
| S03 | 从一段已完成对话创建分支，并检查原聊天和小说文件。 | 分支复制到选择的边界，不复制未结束任务或旧写权限；不回滚现有小说文件。 |
| S04 | 清空聊天、恢复旧聊天，再导出Markdown/JSON并取消一次导出。 | 清空前说明可恢复；旧历史可恢复；导出仅可见内容，不覆盖同名文件、不改稿件，取消无副作用。 |
| S05 | 用开发者提供的有界夹具达到32个非归档会话；尝试新建/恢复，归档一段再恢复；在32个时清空一段。 | 归档不占名额；满额新建/恢复给出说明而不自动挤走其他会话；清空成功后仍32个，旧聊天可查。总容量满的失败分支由开发者离线夹具核对，失败无半归档/半创建、无自动删除；不要求用户填满真实磁盘。 |

建议S01～S05各由至少2位不同用户覆盖；这些本地行为不要求为每个Provider重复付费。32仅限非归档数量，归档仍占总存储；总容量/目录上限在实施合同冻结，不向用户承诺无限历史。

### C. 长篇与自由试写（NR-605）

| ID | 用户任务 | 答案基线/判定 |
| --- | --- | --- |
| L01 | 在长篇工程中询问指定人物职业、关系和事件所在章节，要求给来源。 | 与冻结事实和章节位置一致；每个可核查引用单独记对/错/缺失。 |
| L02 | 根据某章写下一段，使用已确定设定；同时给一个“仅讨论”的备选设定。 | 确定事实保留，未决建议不当成事实、不自动保存。 |
| L03 | 找出测试语料预设的时间线、世界规则或人物能力矛盾。 | 对照预置矛盾位置；误报、漏报分别记录，不只收成功例。 |
| L04 | 较长讨论后询问已确定事项及仍未决定的事项；其中含一次否定/撤回。 | 摘要不丢关键事实、不把撤回/未决说成已定；未实际触发摘要则该子项not_run。 |
| L05 | 请求一次人物设计/情节规划建议，再要求一段明确长度的试写。 | 方法调用有回执；用户分别给实用性、连贯性评分并写例子，不能只问模型自评。 |
| L06 | 按自己的创作习惯自由使用合成小说，记录最卡顿、最困惑及最满意的步骤。 | 记录自然需求、是否完成、人工修正次数；意外问题也进缺陷表，不因不在任务单而丢弃。 |

建议每个拟验证的Provider至少2位用户参加长篇任务；30万字与100万字分别覆盖L01～L03，L04～L06可分配到任一规模。开发者预先准备少量明确目标，避免让用户全文阅读；绝不把整部小说无界发送给模型。开始前确认模型×规模×任务负责人矩阵。某规模没人测时保留not_run，不能以另一规模或机械压力结果替代。

开发者仍离线执行10,000文件/10,000消息边界、预算/截断、冷/热检索P95与内存测试，保留相同机器/语料基线及Hash；同步≤2秒、P95回退>20%须调查的既有约束不变。用户“感觉挺快”是体验反馈，不是这些机械门槛的证据。

### D. 完整创作链（NG-F01/02，NR-604/605）

安排部分用户在同一合成工程连续执行J01～J04；两个目标Provider均须有完整链记录，不把不同起始状态的零散成功拼成一条链。每个子步骤单列pass/fail/not_run/unverified及版本/来源，不要求所有用户重复跑全套。开发者准备合法章节/定稿/来源夹具及预期答案，不能伪造生产回执。

| ID | 连贯任务 | 判定与证据 |
| --- | --- | --- |
| J01 | 讨论一个未与基线冲突的新事实，如“林舟随身携带银色怀表”；明确写并保存指定章节，再让AI依据正式章节维护相关资料。 | 讨论不落盘；实际章提交后才可作为正式来源；人物/资料更新对应章版本与真实回执，事实和建议分开。 |
| J02 | 保留一条后来手动添加的资料备注，修改或撤销作为来源的章节，再查看关联资料状态。 | 原来源失效、资料提示待复核；不自动连带Undo或覆盖后加备注；重开不会重放维护任务。 |
| J03 | 修正并保存章节，明确确认该版定稿；分别测试应用内/外部编辑正文、重开以及再次确认新版本。 | 旧确认失效，需重新定稿；外改不被应用擅自写回；仅残留final字段不可出版。新确认绑定当前版本，Undo不得让失效确认悄悄复活。两条修改路径可分工。 |
| J04 | 确认当前版本后导出本地EPUB，核对正文、章节顺序和产物状态；再试无封面导出。 | 对应有效定稿版本，不混入旧正文、草稿、聊天或内部数据；明确无封面，未宣称已上架。开发者核对回执、输入/产物Hash及ZIP白名单，用户核对可读内容。 |
| J05 | 在独立链副本中制造可控出版预检失败（如未重新定稿或缺必填元数据），随后继续普通聊天；记录试用中实际遇到的资料维护失败。 | 失败不抹掉聊天、已保存章节或既有EPUB。资料维护失败后章仍保存的确定性反例由开发者离线注入；用户未遇到该真实分支则记not_run并与离线证据分列，不反复断网或改权限凑结果。 |

NG-F02所需真实主链与确定性离线故障矩阵分别验收：J01～J04及J05出版失败为真实分配任务；未实际观察到的资料失败分支不冒称真实通过。若发现该分支真实失败则必须修复，不能因已有离线通过而忽略。J01～J03的授权/数据安全项不能用平均评分豁免；语义事实与待复核状态同时进入NR-605评价。

### E. 安装、升级与最终版本（NG-F05，NR-604/606）

| ID | 执行者/检查 | 预期与放行条件 |
| --- | --- | --- |
| D01 | 开发者先在无Node/Rust/开发工具的干净Windows环境检查，至少一位用户复核安装→启动→安全配置→新建工程→聊天/工具入口。 | 记录系统/必要运行时、安装包Hash；不依赖开发机缓存、共享Key或旧状态。用户配置Provider由其自主完成，开发者离线阶段不读真实Key。无法安装/启动不得发放受影响环境。 |
| D02 | 用旧版本生成的单会话合成工程副本升级；开发者核对数据，至少一位用户执行重开/切换/查看/Undo。 | 原session/message身份、History/有效Memory、Canon、Change/Undo和适用章节来源保留；不是复制后重建身份。回退先在副本验证；不让旧程序直接写唯一的新格式工程，不承诺所有降级兼容。 |
| D03 | 开发者对测试版与最终候选版列影响表，安排相关用户复验，固定最终安装包。 | 工具/内置方法、存储/会话、恢复、定稿/出版或相关依赖变化使受影响证据待重测；涉及两个Provider则分别复验。仅文档差异可说明理由复用，最终包仍需安装/启动检查。未知影响扩大回归，不拼接不同版本结果宣称最终通过。 |

以上检查不要求每位用户重复安装/升级。最终报告追加：`测试build、最终build、代码/依赖差异、受影响任务、可复用证据及理由、重跑证据、残留缺口、裁决人`。NR-606在这些材料齐全后提交NR-G7，不能用旧安装包的成功替代最终候选版。

## 6. 判定、缺陷与复测

以下是拟沿用/细化的验收标准，发放前由负责人确认任务矩阵和评分方法；不是已经产生的测试结果。

- 严重安全/数据错误必须为0：泄漏、丢稿、未授权/越界/重复写、手动稿被覆盖、假报保存，任一出现停止受影响批次。不能用总体满意度抵消。
- 阻断关键流程的缺陷（普通聊天被工具失败抹掉/阻断、核心读取或保存不可用、会话恢复损坏等）必须修复、复测；不通过就不能宣称NR-604完成。
- 每个Provider/model的强制关键任务和本地会话任务须按冻结覆盖通过；实际故障为fail，没测为not_run，缺证为unverified，分开计数。核心项缺测/缺证不被忽略。覆盖变更须负责人明确决定，不事后缩小样本来凑通过。
- NR-605核心语义任务完成率≥90%，抽样事实引用准确率≥95%，实用性和连贯性评分分别平均≥4/5；分别按Provider/规模列样本数及所有失败。完成率分母为预分配任务的有效尝试，失败不得删除；覆盖缺口另列并阻止冒称完整通过。引用分母包含应提供却未提供的指定事实来源；评分缺失列缺证。
- 评分锚点：1=无法使用或关键事实错误；2=需大量重写；3=需明显修正；4=少量修正即可用；5=符合任务且可直接用。少量用户平均分不代表统计显著；零严重错误仅表示样本内未发现。
- 易用性/文案/轻微性能问题也登记，负责人按影响分级；不能将功能故障仅改名为“体验建议”绕过修复。未达机械性能约束仍按既有Story处理。
- 每个修复绑定新版本，先完成责任Story的完整质量门，再请原报告者及另一位用户复测；原报告者退出时记录原因并安排两位替代者。保留原fail记录，不用新结果覆盖历史。涉及共享运行时的修复同时补齐受影响Provider回归。无论是否称为bug修复，测试后的功能/依赖改动均按D03评估证据失效范围；NG-F01～NG-F05的验收缺口须在相应Story关闭，文档补齐不等于实现完成。
- NR-604/605是实际测试与结果验收，不是“写完方案/发完安装包”就completed。测试排期等待不倒退NR-G6，但阻止宣称NR-G7完整真实验收已通过。若要缩减支持范围或豁免缺口，需单独产品裁决并如实标记，不能由助手推定。
