# NovelGainker 产品策划案 v1.1

状态：2026-09-09完成Q1～Q17访谈；2026-09-10按T2/T2a补充决定更新：每次对话涉及关键词、别称或指代时自动审核相关上下文，正式审稿仅由作者明确请求触发。原有质量目标和作者验收保留，取消默认阶段/全书审稿安排。本文是目标产品定义，新增行为尚未实现。原始决定见[梳理记录](reviews/project-reframe-2026-09-09.zh-CN.md)，后续修订见[技术访谈](reviews/technical-design-alignment-2026-09-09.zh-CN.md)。

## 产品定义

NovelGainker帮助有故事点子、缺少完稿经验的人，通过与AI持续讨论，逐步完成一部10～20万字的小说。AI承担候选方案整理、已授权范围内的创作执行和资料维护，作者掌握关键创作选择与阶段成果验收。

核心体验是分阶段自主推进。作者不需要逐项操作工具或每写一个片段就发送“继续”；也可以在任何时候插话、纠正或停止。产品将小说内容、执行进度和实际保存结果清楚对应，让作者能判断已经完成什么、还需要决定什么。

## 核心用户与价值

首要用户有题材、场景、人物关系或一句hook，但缺少把它组织成完整作品的经验。产品帮助其完成方向判断、结构设计、持续创作和成稿修订。现有连载作者及稿件评审用户可使用相关功能，但不能以兼顾所有人模糊首版主流程。

首要作品目标为10～20万字完本。原方案的30万/100万字长篇检索、语义与性能验收保留其既有范围；此次选择不自动删除长篇测试，也不承诺百万字自动完本已经实现。

## 最低交付质量（Q12已确认）

交付目标是情节完整、基本一致、可完整阅读的小说初稿。主线有结局，人物动机和世界规则基本一致，重要伏笔已有回收或明确处理，章节包含真实场景与情节，而非扩写梗概或重复凑字数。

字数达标不单独构成成功。系统需要报告未解决的矛盾、待修订段落与检查范围，不能用“检查通过”掩盖已知问题。作者可在此基础上进一步润色语言；产品不承诺未经作者审阅即可商业发布。

## 作者与AI的分工

| 工作 | 默认分工 | 决策来源 |
| --- | --- | --- |
| 缺失的姓名、身世、反派动机、结局等 | AI先整理一份可讨论的完整候选，明确哪些为新建议 | Q5 |
| 故事方向及主线 | 作者确认 | Q2、Q4、Q5 |
| 大纲与故事阶段划分 | AI提出可读方案，作者确认 | Q4 |
| 首章 | AI起草，作者验收以校准风格和节奏 | Q4 |
| 已确认方向内的普通场景细节 | AI自主补全 | Q5 |
| 同阶段内多章创作 | AI连续推进，按阶段交付验收 | Q2、Q4 |
| 主线或主要人物动机发生变化 | 先回到作者处确认 | Q5 |
| 本阶段新增事实 | 自动记录为暂定事实，后文遵循，随阶段验收确认；不得覆盖冲突的已确认设定 | Q6 |
| 自行修稿 | 可修订当前阶段未验收草稿，保留可回看版本；修改已验收章节或已确认主线前征求作者决定 | Q7 |
| 执行中改方向 | 暂停后续执行，保留已完成内容，说明影响；作者确认调整后的方向后继续 | Q8 |
| 阶段不满意 | 先提出保留/改写范围与原因，作者确认后自主返工并复查相关事实，保留旧版本 | Q13 |
| 全书定稿 | 汇总已有上下文审核、实际成果和未决问题，由作者整体确认当前全书版本再导出；不自动启动正式审稿 | Q14、T2 |

AI读取方法、校验格式、保存与核对文件属于执行职责。作者确认应围绕创作意义和结果，不以“修工具参数、选择schema、处理内部循环预算”作为常规写作步骤。

## 主流程

1. 作者输入故事想法，可从一句hook开始，不要求事先填写完整设定表。
2. AI识别已给定内容和缺口，提出完整候选方向；作者讨论、修改并确认。
3. AI展开人物、世界规则和大纲，将全书分成可验收的故事阶段；作者确认整体方向和结构。
4. AI写首章，作者验收风格、叙述视角和节奏。
5. AI在批准阶段内连续创作，维护必要资料和执行进度，在阶段验收点交付。
6. 作者验收、修改要求或提出新的方向；下一阶段使用有效的当前版本继续。
7. 全书完成后汇总已有上下文审核结果、目标完成情况及剩余问题，在已批准范围内处理改动；作者整体确认当前全书版本定稿，再本地导出EPUB，无需逐章重复确认。没有作者审稿请求时不新增全书审稿任务，也不将局部审核汇总宣称为全书已审。

## 阶段如何划分

故事阶段围绕一个清晰的情节目标组织若干章节，例如“入狱并结识同伴”或“查出证据的来源”，而非按模型调用次数划分。AI在大纲中提出每阶段的目标、章节范围、预计篇幅和主要成果，由作者确认；阶段范围不会在执行中悄悄扩大。

方向候选应包括主线、人物核心动机、主要矛盾与结局方向；大纲说明阶段目标和因果关系；首章用于校准叙述视角、语言和节奏；阶段验收交出实际章节、资料变化、检查结果和未决问题。AI新提的创意明确可辨，作者已有输入不会被当成可任意覆盖的建议。

## 对话上下文审核与主动审稿（T2、T2a已确认）

每次对话涉及已有的人物、物件、地点、事件、时间或设定时，系统自动识别关键词并核对相关上下文。关键词包含别称及结合前文能确定的指代，例如“小吏”“男主”“他”和“铜钱”“那枚钱”；不只做名称完全匹配。指代有多个合理对象时简短澄清，不随意绑定。

自动审核围绕当前话题读取有关设定、章节原文和对话背景，区分作者已确认事实、阶段暂定事实与聊天中的候选想法。发现矛盾时指出依据，让讨论基于正确上下文继续；不因命中关键词自动改稿、改设定或发起正式审稿。与话题无关的内容不为此重读整本书。AI在生成中引入新的相关实体或事实时也要补齐必要上下文，不能仅核对用户输入而任意补出冲突事实。

例如，前文铜钱已经交给狱卒，作者说“他用那枚钱买通守卫”，系统应自动找回铜钱去向并提示需要交代如何取回；作者仍可讨论“改成先偷回铜钱”的候选，不会因此被迫先通过整阶段审稿。正式保存改动继续遵守Q5～Q7、Q16和Q17的授权边界。

正式审稿是作者主动要求的评阅任务，可涉及结构、节奏、人物塑造、语言和全文问题。例如作者说“帮我审一下第五章”，才启动该范围的审稿；要求整书审稿才扩大到全书。阶段结束、全书完成、关键词命中及AI自行觉得有必要都不构成审稿请求。自然语言等价请求也可识别，但引文里出现“审稿”、讨论如何审稿或明确说不要审稿不触发执行。

阶段验收仍由作者决定，交付实际章节、资料变化、已有核对结果和未决问题，不以完成一份未请求的正式审稿报告为前置条件。局部上下文审核不能标为“全书审稿通过”。正常写作的格式、版本、保存和相关事实核验继续执行；正式审稿没有被请求时不发生对应模型调用、预算预留或质量润色循环。主动审稿仍受预算限制，审稿请求本身不自动授权修改正文。

G01～G08已确认补充：上下文关联需维护改名、重名与指代，事实需考虑故事时间和人物知情范围；聊天里的批准应可靠衔接资料保存。发现冲突要保留依据及处理决定，避免重复询问；流式内容补查后再按T1保存显示，已显示错误明确更正。核对失败仍可在真实能力范围内讨论候选；阶段完成以目标和成果为依据，反复改写不算持续进展。详细技术规则见[缺口处理方案](reviews/technical-gap-closure-proposal-2026-09-10.zh-CN.md)，其中1～15现均已确认，实施及验证尚未完成。

## 阶段内的内容与控制

阶段内自动补充的细节记录为暂定事实，后续章节应遵循同一有效版本；阶段验收后才转为已确认。遇到与已确认设定的冲突，AI不能自行覆盖旧事实来消除冲突。暂定内容也应可以被作者查看，不能只有模型自己知道。

AI可修订当前阶段未验收的草稿，保留可回看版本。改动已验收章节或已确认主线前，先说明改动范围与影响，等待作者决定。当作者笼统否决阶段时，先分析问题，提出保留/改写哪些章节及原因，经作者确认范围后自主返工，不要求作者逐句指导。返工保留旧版本，并复核相关暂定事实。跨阶段改动按Q16处理：先列出受影响的章节和设定，由作者一次确认整组修改范围；修订完成后仅重新验收受影响部分，其余保留原验收结果。

作者执行中改变主线时，暂停后续执行并保留已完成内容，先说明影响；确认调整后的方向后再继续。普通补充或闲聊是否改变执行目标，应依据语义区分，不能把每条新消息都当重写指令。

## 作者直接编辑（Q17已确认）

作者手动保存的修改作为当前文稿保留，AI检查人物资料和后文是否与之不一致。当前未验收阶段内的普通细节可以同步；涉及已验收内容、主线或主要人物动机时，先说明影响并征求作者决定。AI不能依据旧设定悄悄把作者手改改回去。

作者手改不等于批准AI任意改写全书。未保存的编辑继续受到保护；保存导致的版本与检查失效如实展示，不能保留旧“已验收/已定稿”标记冒充新版本获批。

## 阶段验收与全书定稿

阶段验收表示作者认可该阶段当前成果及有效暂定事实；它不自动替代全书定稿。已验收内容后续受修改保护，修改前按Q7确认。

全书完成时，系统交出整稿、已有上下文审核及受请求审稿的结果与剩余问题；获准修订后，作者对当前全书版本整体确认一次，随后生成本地EPUB。未请求正式审稿时，不把正式审稿设为定稿前置条件；仍需核对实际版本、合法格式、有效作者决定和已知问题。全书确认须绑定实际章节版本，不能以一条历史“同意”覆盖后来产生的内容。文件保存、阶段验收、全书定稿和EPUB生成分别显示真实状态。

阶段验收同时展示本阶段成果、下一阶段目标及费用估算。作者明确“通过并继续”可一次完成验收与下一阶段授权，也可以只验收暂不继续；普通称赞不作为执行授权（Q15）。跨阶段返工只重新验收受影响部分（Q16）；手改同步按Q17处理，不从“阶段自主”推导无限后续授权。

## 故障、费用与恢复

在阶段授权范围内，系统自行处理短暂可恢复网络故障和可纠正的工具参数错误。两者处理不同：网络故障有限重试，参数错误根据具体反馈修改后再执行；不能用重复发送相同错误请求代替纠正。已经成功保存的步骤不因后续回复失败而重新执行。

持续失败、无进展或不能确定副作用结果时，保留内容和进度，说明停点并暂停。系统故障不应常规转嫁成作者必须重新输入任务或点击整轮重试；暂停后恢复应继续未完成工作。

预算优先。产品提供可调整的默认预算与阶段费用估算，接近或预计超过预算时暂停，作者决定是否追加。质量改善不能授权无限模型调用；估算不是服务商最终账单。计量与预留规则在技术方案中落实，不能承诺无法核实的精确费用。

关闭应用后停止执行，不在后台继续生成。已完成内容和可恢复进度保留；重开展示停在哪里、尚缺什么，经作者确认继续后恢复，无需重述原任务。程序异常退出也应能够恢复到可核对的进度点，不重复已提交写入。

这些是Q9～Q11确认的新目标行为，取代旧产品策略中的零自动网络重试；当前代码尚未完成对应改造。

## 保留的产品基线

- Windows、本地工程、简体中文界面，三栏分别承担工程与会话/Provider、自然对话、真实文稿编辑。
- 小说Markdown及受控资产为稿件来源；聊天历史、派生记忆和执行记录不作为小说正文出版。
- 多会话共享当前稿件；聊天分支不回滚稿件。32个非归档会话是既有决定，不在本轮重复批准。
- 实际文件保存、版本定稿和EPUB生成是不同结果，不能仅依据AI文字宣称成功。
- 不含工程云同步，不自动增加平台上架或图片生成承诺。

实现分层、工程候选参数与验收用例见[技术方案](technical-design.zh-CN.md)。实现方案不能反过来扩大已确认的创作或费用授权。
