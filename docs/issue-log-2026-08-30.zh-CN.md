## 1. 开发环境与桌面应用启动

### 现象

首次启动开发模式时，Rust 编译/运行阶段无法读取一部分随仓库提供的资源文件，桌面应用未能正常启动。

### 原因

Windows Git 的 `core.autocrlf=true` 将部分受哈希锁定的内嵌资源转换为 CRLF 行尾。资源包和合约锁会按字节验证内容，行尾变化会使验证不一致。

### 已处理

- 将本仓库 Git 行尾策略调整为不再自动转换。
- 将受影响的资源恢复为 UTF-8（无 BOM）和 LF 行尾。
- 安装并确认开发所需环境：Node.js、pnpm、Rust MSVC 工具链、Visual Studio Build Tools、Windows SDK、WebView2。
- `pnpm dev` 已可启动，桌面进程可正常运行。

### 后续注意

不要对 `resources/` 下受锁定保护的文件批量改行尾或编码。重新克隆后应先检查 Git 行尾配置再安装依赖。

## 2. Agent 报错：`agent-action.repair-exhausted`

### 现象

Agent 在同时路由到 `create-setting` 与 `create-plot` 时显示：

```text
Agent 操作格式未通过校验
错误代码：agent-action.repair-exhausted
```

### 诊断结论

- 该 Turn 选中了两个 Skill，但未产生任何工具调用或项目写入。
- Provider 的初次输出和一次修复输出都没有通过 `AgentActionPayloadV1` 与应用策略校验。
- 原实现将第二次失败统一折叠为 `agent-action.repair-exhausted`，未保存原始 Provider 回复或具体字段错误，因此无法从既有本地记录恢复“哪个字段不合规”。
- Agent 合约本身允许多 Skill；运行时最多可选择 4 个 Skill，且已有 `create-setting + create-plot` 的合约测试。

### 已修复

此前授权逻辑要求 Provider 返回的 `skillIds` 数组与当前 Turn 的顺序逐项完全一致。多 Skill 时，Provider 仅交换相同两个 ID 的顺序也会被错误拒绝。

现已改为：返回的 Skill 集合必须与冻结集合完全相同，但不再要求顺序相同。仍会拒绝以下情况：

- 漏掉任一已选 Skill；
- 包含额外 Skill；
- 包含重复 Skill。

同时更新了 Provider 指令，明确多个 Skill 必须使用一个 JSON 对象和一个完整的 `skillIds` 数组，不能拆分为多个计划。

相关代码：`apps/desktop/src-tauri/src/agent_commands.rs`。

### 验证

已通过以下测试：

- 多 Skill 返回顺序互换时可被接受；
- 缺少一个已选 Skill 时仍会被拒绝；
- Agent 命令相关单元测试：5/5 通过；
- `cargo fmt --check` 通过；
- `cargo clippy -p novelgainker-desktop --lib --tests --locked --offline -- -D warnings` 通过。

### 待验证

需要在桌面应用中再次用 DeepSeek 发起“设定 + 主线规划”请求，确认实际 Provider 响应能通过。若仍失败，则问题是 Provider 返回了非 JSON、缺少必填字段或其他无效内容，而不是多 Skill 的顺序问题。

## 3. 本机偏好报错：`app_state.unavailable`

### 现象

应用显示：

```text
本机偏好暂不可用
错误代码：app_state.unavailable
```

### 已确认事实

- 本机状态库位于 `%APPDATA%\com.novelgainker.desktop\app-state-v1.sqlite3`。
- SQLite `PRAGMA integrity_check` 返回 `ok`。
- 外键检查没有发现冲突，数据库用户版本为 `10`，表结构与当前程序一致。
- 当前用户拥有该文件的写入权限。
- 数据库中有一条指向不存在目录的旧最近项目记录，路径类似 `\\?\D:\��`；名称/路径存在乱码。

### 限制与判断

`app_state.unavailable` 是应用把多种偏好读写失败统一映射后的通用代码。当前实现会在首次 SQLite 操作或记录校验失败后把状态库标记为 `Degraded`，但不保留底层数据库错误；因此不能仅根据该代码断言数据库“已损坏”。

本次只做了只读与回滚式诊断，未删除或修改状态库。

### 建议修复（需明确授权后执行）

1. 关闭 NovelGainker。
2. 备份 `%APPDATA%\com.novelgainker.desktop\app-state-v1.sqlite3`。
3. 将原数据库移动到备份名称，让应用启动时创建新的状态库。
4. 重新打开项目并检查 Provider 设置。

此操作会重置最近项目、界面偏好和本地 Agent 历史，但不会删除项目目录中的 Markdown 内容。系统凭据库中的 API Key 通常不会被删除，不过可能需要重新选择 Provider。

## 6. 功能需求：已部署小说工作区的读取入口

该功能应能让用户选择或打开工作区根目录，并识别其中已有的项目结构与内容，随后加载作品的基础信息、目录和 Markdown 文件到工作区界面。用户不应需要通过重新新建项目或逐个手动打开文件来继续既有作品。

### 验收方向

- 能选择一个已存在的、符合项目规范的小说工作区；

- 能显示该作品的项目资料、章节及已有素材；
- 打开失败时给出可理解的原因，并保持项目文件不变；
- 与“最近项目”和当前文件恢复逻辑兼容，但不依赖它们才能打开项目。
