## 1. 开发环境与桌面应用启动

### 现象

首次启动开发模式时，Rust 编译/运行阶段无法读取一部分随仓库提供的资源文件，桌面应用未能正常启动。

### 原因

Windows Git 的 `core.autocrlf=true` 将部分受哈希锁定的内嵌资源转换为 CRLF 行尾。资源包和合约锁会按字节验证内容，行尾变化会使验证不一致。

### 已处理

- 将本仓库 Git 行尾策略调整为不再自动转换。
- 将受影响的资源恢复为 UTF-8（无 BOM）和 LF 行尾。
- 安装并确认开发所需环境：Node.js、pnpm、Rust MSVC 工具链、Visual Studio Build Tools、Windows SDK、WebView2。
- `pnpm dev` 已可启动，桌面进程可正常运行。

### 后续注意

不要对 `resources/` 下受锁定保护的文件批量改行尾或编码。重新克隆后应先检查 Git 行尾配置再安装依赖。

## 2. Agent 报错：`agent-action.repair-exhausted`

### 现象

Agent 在同时路由到 `create-setting` 与 `create-plot` 时显示：

```text
Agent 操作格式未通过校验
错误代码：agent-action.repair-exhausted
```

### 诊断结论

- 该 Turn 选中了两个 Skill，但未产生任何工具调用或项目写入。
- Provider 的初次输出和一次修复输出都没有通过 `AgentActionPayloadV1` 与应用策略校验。
- 原实现将第二次失败统一折叠为 `agent-action.repair-exhausted`，未保存原始 Provider 回复或具体字段错误，因此无法从既有本地记录恢复“哪个字段不合规”。
- Agent 合约本身允许多 Skill；运行时最多可选择 4 个 Skill，且已有 `create-setting + create-plot` 的合约测试。

### 已修复

此前授权逻辑要求 Provider 返回的 `skillIds` 数组与当前 Turn 的顺序逐项完全一致。多 Skill 时，Provider 仅交换相同两个 ID 的顺序也会被错误拒绝。

现已改为：返回的 Skill 集合必须与冻结集合完全相同，但不再要求顺序相同。仍会拒绝以下情况：

- 漏掉任一已选 Skill；
- 包含额外 Skill；
- 包含重复 Skill。

同时更新了 Provider 指令，明确多个 Skill 必须使用一个 JSON 对象和一个完整的 `skillIds` 数组，不能拆分为多个计划。

相关代码：`apps/desktop/src-tauri/src/agent_commands.rs`。

### 验证

已通过以下测试：

- 多 Skill 返回顺序互换时可被接受；
- 缺少一个已选 Skill 时仍会被拒绝；
- Agent 命令相关单元测试：5/5 通过；
- `cargo fmt --check` 通过；
- `cargo clippy -p novelgainker-desktop --lib --tests --locked --offline -- -D warnings` 通过。

### 待验证

需要在桌面应用中再次用 DeepSeek 发起“设定 + 主线规划”请求，确认实际 Provider 响应能通过。若仍失败，则问题是 Provider 返回了非 JSON、缺少必填字段或其他无效内容，而不是多 Skill 的顺序问题。

## 3. 本机偏好报错：`app_state.unavailable`

### 现象

应用显示：

```text
本机偏好暂不可用
错误代码：app_state.unavailable
```

### 已确认事实

- 本机状态库位于 `%APPDATA%\com.novelgainker.desktop\app-state-v1.sqlite3`。
- SQLite `PRAGMA integrity_check` 返回 `ok`。
- 外键检查没有发现冲突，数据库用户版本为 `10`，表结构与当前程序一致。
- 当前用户拥有该文件的写入权限。
- 数据库中有一条指向不存在目录的旧最近项目记录，路径类似 `\\?\D:\��`；名称/路径存在乱码。

### 限制与判断

`app_state.unavailable` 是应用把多种偏好读写失败统一映射后的通用代码。当前实现会在首次 SQLite 操作或记录校验失败后把状态库标记为 `Degraded`，但不保留底层数据库错误；因此不能仅根据该代码断言数据库“已损坏”。

本次只做了只读与回滚式诊断，未删除或修改状态库。

### 建议修复（需明确授权后执行）

1. 关闭 NovelGainker。
2. 备份 `%APPDATA%\com.novelgainker.desktop\app-state-v1.sqlite3`。
3. 将原数据库移动到备份名称，让应用启动时创建新的状态库。
4. 重新打开项目并检查 Provider 设置。

此操作会重置最近项目、界面偏好和本地 Agent 历史，但不会删除项目目录中的 Markdown 内容。系统凭据库中的 API Key 通常不会被删除，不过可能需要重新选择 Provider。

## 7. GAR1 对话一直“AI 活动中”，停止后一直“正在停止”

### 现象

- 用户发送消息后，Turn 已进入活动态，但中栏没有 AI 进度提示或回复；
- 点击“停止”后，界面一直停留在“正在停止”，输入框无法恢复。

### 根因

Rust 的 `AgentTurnEventBodyV2` 只对枚举 Variant 应用了 camelCase，Variant 内字段仍被序列化为 snake_case，例如 `visible_reason`、`selected_skill_ids` 和 `agent_canon_write_count`。前端严格事件协议只接受 `visibleReason`、`selectedSkillIds` 和 `agentCanonWriteCount`，因此状态、Skill、来源以及 completed/failed/cancelled 终态事件被安全拒绝。取消请求本身已经送达，但 cancelled 事件同样被丢弃，造成 UI 无法退出活动态。

### 已修复

- Rust 事件体字段统一序列化为 camelCase；
- 增加真实 Rust JSON 形状回归，锁定状态、Skill 和取消终态字段；
- 前端在事件通道订阅完成前禁止发送，消除启动时事件丢失窗口；
- 首个 Conversation Delta 到达前，中栏显示当前处理状态和可见原因；
- 增加“发送 → 首包前提示 → 停止 → cancelled 终态 → 输入恢复”组件回归。

### 验证

- 定向 Rust 事件序列化测试通过；
- `AgentConversation` 组件测试 3/3 通过；
- 完整 `pnpm quality` 通过：159 个前端测试、37 个桌面 Rust 测试、严格 Clippy、Debug/Release Build 与窗口 Smoke、NG-R101～NG-R106 和 GAR1 技术证据全部通过；
- 生产边界仍为 28 Command / 7 Agent IPC，Agent Canon 写入仍为 0。

必须关闭旧进程并使用重新构建的 `target/release/novelgainker-desktop.exe`。当前授权不包含真实 Provider Live Smoke，因此仍需用户使用既有 Provider 配置发送一次普通对话，并确认回复、停止和下一轮输入均可正常终态化。

## 8. GAR1 稀疏工程回复失败与窗口退出前置

### 现象

- 取消链路恢复后，同一条“继续广东之王故事”的请求可以进入终态，但最终显示 `failed`；
- 点击窗口关闭按钮时，桌面运行仍可能要求先在左栏关闭项目。

### 根因

- 当前工程只包含项目标题等少量 Canon。Context Index 把一个语义查询中的多个 `terms` 拼成单一长短语后统一评分；因此 `岭南 / 流放书生 / 广东之王` 中明明有单项命中项目标题，仍可能被整体判为零来源；
- Control Host State 只回传累计来源，不回传已经执行过但零命中的查询。Provider 看见空来源后可能重复相同 `request_context`，直至控制轮次上限并安全失败；
- 前端完成项目清理后调用 Tauri `close()`，会再次触发 `close-requested`。真实桌面事件时序下存在二次拦截竞态，而组件 mock 没有模拟这一重入行为。

### 已修复

- Context Index 将多个 `terms` 作为语义备选项分别匹配，同时继续使用合并 n-gram 排序；
- Control Host State 增加有界的 `completedContextQueries / lastQueryHadNoMatches`，固定系统指令禁止重复已完成查询，并要求无更多来源时以空 `sourceIds` 的 `start_response` 进入独立 Conversation；
- 窗口关闭仍同步保护未保存编辑，并自动尝试关闭项目；完成或跳过 best-effort 清理后直接 `destroy()` 窗口，不再二次触发关闭拦截器；
- 保持 GAR1 只读边界、Provider/Skill 快照、累计预算与零 Agent Canon 写入不变。

### 回归

- 增加“多词查询中任一精确锚点可命中 `project.md`”Rust 回归；
- 增加“空查询历史进入下一轮 Control 且明确要求 `start_response`”Rust 回归；
- 双 Provider 请求序列化测试锁定固定空查询规则；
- 窗口关闭组件回归改为验证 `project_close → destroy`，并继续覆盖 dirty buffer 与清理失败场景。

### 待用户实机确认

真实 Provider Live Smoke 未获授权，不由质量门读取既有密钥或产生调用费用。完成 Release 重建后，由用户重试同一条消息，并验证窗口可直接关闭；若仍失败，界面会保留稳定错误码用于下一轮定位。

## 9. “继续 / 重试”失败、稀疏工程回复过度保守与 `runtime.unknown`

### 现象

- 首轮 DeepSeek Conversation 能返回正文，下一轮“继续”却直接显示“本次回复未完成”；再次发送“重试”仍失败；
- 首轮正文要求作者补充不存在的 Draft、章纲或状态清单，没有按空工程的一句 premise 共同推进；
- 点击窗口关闭按钮时显示“系统检查未完成”，错误码为 `runtime.unknown`。

### 定位结论

- 工程内 Agent History 显示，最近一个成功 Turn 已选择 `novel-story-telling` 并完成 Conversation；后续两个失败 Turn 的 `selectedSkillIds` 均为空，且没有来源。因此技术失败发生在完整 Skill Bundle 加载和 Conversation 之前，不能归因于 novelist Skill 正文“限制 AI”；
- 旧 Skill Selection 只收到当前一句“继续 / 重试”，看不到承接语义；非 `product_help` 意图又禁止空 Skill，导致短承接语容易在选择阶段安全失败。History 未持久化该瞬时错误的精确稳定码，所以这里按阶段证据定位，不虚构 Provider 原始错误；
- `novel-story-telling` 本身允许规划、写作和继续故事，并未要求空工程必须先存在 Draft。首轮回复过度保守来自 Conversation 层没有明确区分“共同创作稀疏工程”和“无缝续写既有正文”；
- 窗口逻辑已经改用 `destroy()` 避免 `close-requested` 重入，但 Tauri Capability 仍只授权 `close`，缺少 `core:window:allow-destroy`。权限拒绝再经通用错误映射后显示为 `runtime.unknown`。

### 已修复

- Skill Selection 增加 `priorSelectedSkillIds` 承接元数据；Host 只取最近成功、非空的 Skill 选择，忽略失败空选择；
- 不向 Skill Selection 重发上一轮小说正文、上下文摘录或 Memory，避免为了修复承接语义扩大 Provider 数据披露；
- 固定 Skill Selection 指令明确：只有 `product_help` 可以选择空 Skill，其他意图必须在 eligible 集合内选择 1～4 项；“继续 / 重试”应参考 Host 提供的上一轮 Skill ID；
- Conversation 固定指令明确：普通协作讨论不以 Canon、人物卡、设定或 Draft 完整为前置；空工程、标题或一句 premise 都应主动共同推进；仅在作者明确要求无缝续写既有正文且缺少必要接续文本时请求材料；
- Capability 增加 `core:window:allow-destroy`；若原生窗口销毁仍失败，前端显示稳定 `runtime.unavailable`，不再伪装为未知系统错误。

### 回归

- 增加“失败空 Skill 选择不覆盖最近成功选择”的 History 回归；
- 增加“承接输入只含 prior Skill ID 和当前消息，不含历史正文”的桌面 Rust 回归；
- 双 Provider 序列化回归锁定 Selection 承接规则和稀疏工程 Conversation 规则；
- 增加窗口销毁被拒绝时稳定显示 `runtime.unavailable` 的组件回归。

### 待用户实机确认

真实 Provider Live Smoke 仍未获授权。Release 重建后需要用户用现有配置验证：首轮一句 premise 后发送“继续”能进入 Conversation；回复不会强制索要不存在的 Draft；窗口可以直接关闭。若 Provider 仍失败，应记录右栏本次 Turn 的稳定错误码，以区分 Provider 网络、限流与协议校验问题。
