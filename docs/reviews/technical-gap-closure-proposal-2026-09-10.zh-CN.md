依据：用户先要求一次列全问题，随后明确“1-8按建议，然后9-15你也给我出一版建议”。本文件沿用那份15项清单，编号G01～G15，避免与原Q/T/TD编号混淆。

状态：G01～G08先前已确认；用户随后对9～15整套建议答复“按建议”，G01～G15现均已确认。这里的确认是设计选择，不是实现或验证通过。技术主方案见[技术方案](../technical-design.zh-CN.md)，产品要求见[产品策划](../product-spec.zh-CN.md)，原访谈见[专项记录](technical-design-alignment-2026-09-09.zh-CN.md)。不再逐条发问。T3/T5随G11、T4随G12一并确认，原问题不再催答。

## 一、G01～G08：已确认的处理方向

### G01 实体、别称与指代的生命周期

为人物、物件、地点等分配稳定的实体身份，名称和别称只作关联，不当主键。首次打开建立派生索引，保存/外部修改后增量更新；新名称、改名、删除和重名分别处理。相同名称不自动合并实体；别称关联必须有原文或作者决定依据，多个合理对象时保留候选并澄清。

“他”“那枚钱”的解析使用本轮及相关前文，不把某次指代永久变成全项目别名。缓存隔离物理工程作用域、会话指代背景、实体身份和来源版本；工程副本与另一个会话不能串用临时指代。删除来源使引用失效，但不删除历史证据。索引可以重建；检索无命中只代表未找到依据，不能机械证明不存在这个实体。

验收反例：两个同名人物、改名后旧称、被删除的资料、隔离会话中不同的“他”、跨轮“那枚钱”、未完成索引时无命中。错误绑定不得产生新写入权限。

### G02 事实的故事时间与知情范围

事实引用除来源版本及确认状态外，关联事件/场景、故事时间的适用范围、叙述视角及人物知情范围。故事时间与文件修改时间分开；章序也不直接等于时间，允许倒叙、插叙和先后关系未知。未给定的时间不由Host猜出精确日期。

例如“第二章主角持有铜钱”“第三章交给狱卒”表示转移，不应直接判成矛盾。角色台词、谎言、猜测与客观叙述分别标记；某人物未知的秘密不能因为作者或读者已经知道就被他用于行动。只在可比较的时点、条件和叙述层面核对矛盾，资料不足标待澄清。语义判断需要来源，字段本身不能证明故事理解正确。

验收反例：物件转移、伤势随时间变化、回忆、谎言、角色误解、尚未揭示的身份及时间未知。

### G03 聊天确认到正式资料的衔接

候选绑定不可变的真实消息/展示版本；批准记录关联该候选、范围及目标资料。保存准备只能把获准内容转换为受控文件表示，不能趁生成资料补入未批准的主线。Host增加固定元数据，创作文字的变化需符合原授权。

顺序为候选快照 → 作者决定持久化 → Canon写入意图 → 实际Committed → 来源及事实引用登记。中断时记录“已确认、尚未保存”或“已保存、登记待恢复”，按原决定与回执补齐，不能当作用户需要重新确认的新方案。后续上下文在批准待保存时仍可引用该作者决定作讨论依据，但不得宣称资料已经存在；依赖正式资料的写入等提交/登记核对后继续。

方向/大纲、人物和世界资料的目标位置及字段在G09协议中明确，避免StagePlan中仅有简略目标、完整创意却只留在聊天。批准不自动扩大章节范围，缺少源证据时不从摘要还原假批准。

验收反例：批准后崩溃、资料保存后回执登记失败、重复点击确认、候选被更新、保存准备夹带新增主线。

### G04 上下文补查与流式显示

已有相关上下文先取证，再生成回答。生成中引入尚无依据的新实体或既有事实断言时，以语义片段为边界暂缓发布受影响内容，补查相关来源；不能把半句未核实断言作为既定事实先显示。确认是新创意时按候选表达，缺证时明确说明，不假装有原文支持。

发布顺序为相关事实核对或明确候选/缺证状态 → 可见片段持久化成功 → UI发布。无关寒暄和已有依据的片段不需等待整轮全文检查；不逐句发起独立编辑审稿。T1的0.2～0.5秒是持久批次刷新目标，不包括模型和补查等待时间，不承诺总延迟只有半秒。

已显示内容后来因新证据发现错误时，追加关联原片段的更正及依据，保留原始可见记录；不静默篡改历史。上下文核对不能保证模型永不误解，因此还需G15的漏检和误判评估。涉及正式稿件的更改继续经过授权与Canon提交。

验收反例：流中出现新物件、补查失败、预算不足、已发布片段被新证据推翻、发布前后崩溃及重复事件。

### G05 多来源冲突的处理闭环

冲突记录绑定相关实体/事实、双方来源版本、适用故事时间、影响范围及当前处理状态。人物文件、正文和设定文件之间不凭文件类型或最后写入时间自动定胜负；作者手改保持原样，同时展示不一致。

作者的澄清、保留两种说法或批准修订范围形成可恢复决定；同一冲突在相同版本下不反复询问。来源或范围有实质变化才重新打开，并说明新证据。澄清记录不直接修改稿件；必要修改经G03及既有写入权限生效。保持“作者已决定”“文件已改”“关联事实已复核”三种状态可区分。

验收反例：正文与人物资料不一致、同一冲突跨轮重复、已决定后原文再次变化、作者选择保留角色的错误认知。

### G06 审核失败后的有限降级

| 当前条件 | 可以继续什么 | 必须如实限制什么 |
| --- | --- | --- |
| 有足够当前来源且有有效预算 | 依据已取证范围回答或继续获准工作 | 不声称未读部分已核对 |
| 部分来源缺失，但仍能发请求 | 讨论明确标为候选的设想，解释缺证和待核对项 | 依赖未知事实的提交暂停；不输出“审核通过” |
| 网络不可用、预算不足或持久状态不可用 | 本地显示已保存内容、错误原因和恢复入口；仍可用的本地编辑按原合同执行 | 不虚构模型回复、不绕过请求预算/持久化；无法可靠保存时也不假称已保存 |

给本轮必要答复留出请求/输出空间；若无法保留，先停止继续取证而不是耗尽额度后无话可说。简单故障说明由Host状态投影，不为解释“预算不足”另发付费请求。降级讨论使用真实作者输入与已知上下文，不能变成扩大写入权限的旁路。

验收反例：读取额度耗尽、金额额度不足、来源文件消失、Provider持续不可用、状态盘写满。

### G07 阶段目标到完成证据的对应

StagePlan把批准目标拆成有身份的目标项，关联预定章节/场景及明确结果，例如“同伴完成越狱”，并区分硬性成果与可调整表现方式。WorkStep提交时关联实际章节、结果摘要和依据；这些是创作过程记录，不在阶段末偷偷启动一次完整审稿。

写够章数/字数、模型Stop或Task成功均不直接完成目标。协调器核验所需成果和关联版本是否齐全，语义达成依据如实呈现，最终由作者验收；不能宣称Host能证明情节质量。目标缺项时仍在原范围/预算内继续，发现需扩大主线或阶段范围则提出变更。作者验收旧快照不授权新增目标。

验收反例：三章写完但尚未越狱、章数增加但目标未推进、目标已在前章达成、提交后手改使证据过期。

### G08 防止反复改写被算成进展

进展关联批准目标、首次取得的有效来源、已列问题的修复证据及稳定的成果版本；不以新Hash、新callId或新run本身计进展。记录同一目标/内容的重复修订、A→B→A回摆，以及问题关闭后反复重开；循环不能刷新累计预算、连续失败及无进展窗口。

有限窗口内无净推进即保留当前版本和问题清单暂停，给出具体停点；阈值由故障及创作样本校准。作者明确要求的新返工可建立新的获准目标，但不抹掉历史费用。候选版本比较只用于识别重复，不直接判定哪个版本文学上更好。

验收反例：标点来回变化、同段A/B互换、重复解决同一问题、以重新建立步骤绕过累计限制。

## 二、G09～G15：整套处理方向已确认

### G09 工具参数、候选格式与纠错

推荐保留read_context、propose_change、publish三个能力入口，明确升级协议版本。使用一份类型化合同派生Host校验、双Provider工具定义和边界样例，避免三处各写一套字段。模型负责内容和意图；Host负责目标身份、合法相对路径、固定frontmatter、序列化及事务，不让模型手写UUID或自由拼文件路径。

写入按内容种类及动作分支，至少明确目标引用、已有源版本/完整读取回执、获准范围和创作正文；新建与更新分别要求必要字段。方向/大纲的完整内容要有受控Markdown表示，不能只放在运行目标摘要中；新增表示须与现有五类资料/章节合同及检索共同验证，不私自塞入不支持字段。更新保留非目标内容并做CAS，不能以格式化为名覆盖作者手改。

方法请求返回完成操作所需模板/字段约束；超额分段并收齐回执后才允许使用。失败反馈提供有界的字段位置、期望类型/允许值、修正提示、可纠正性及副作用状态。格式错误只在无副作用时自动纠正；权限/来源冲突重新取证或暂停依赖写入，不转成放宽校验。

验证出口：同一语义请求在双Provider得到等价Host结果；缺字段、未知字段、非法目标、超长正文、过期原文、缺模板及错误参数修正均有定向样例；已提交效果不会因纠错再次执行。原截图错误需可重现、可定位、可恢复，才能称修复。

### G10 普通聊天、阶段工作与不确定费用

推荐单一请求账本、分开用途额度：普通聊天/前期规划使用预先展示并获准的聊天额度；阶段工作使用获准阶段额度；主动审稿关联其真实请求及对应额度。一次物理请求只记一次费用，以用途归属和共同总额防止重复记账或偷偷挪用。若设置总预算，请求同时满足用途额度与总额度；不得通过另开会话/run重置已有任务用量。

默认聊天额度在首次配置时集中设置，日常发送在已授额度内不重复确认；追加或扩大用途时才呈现决定。阶段报价包含上下文审核、写作、必要恢复，未请求审稿不预留审稿费用。读取/纠错和最终答复共同占用本轮限额，先给正常答复留空间。

不确定费用单独显示并保守占用原预留：可靠usage/对账到达才调整，不能超时释放或展示为实际账单。没有可靠结算途径时不强制等待永远不会来的事件；告知仍占用多少，作者可在看见已用与不确定量后追加额度继续。追加不清除原记录，也不声称平台免收费。金额上限没有可靠价格时继续沿用已批准规则：暂停该付费工作，补全价格或由作者明确选择其他额度单位。

验证出口：正常聊天、阶段内多轮、显式审稿、Compactor、超时重发、重开和额度追加统一核对；预留/已观测/不确定三类互不混淆，不存在无budgetId的实际发送。

### G11 插话与归档：合并原T3、T5

推荐普通输入优先：新消息先持久化并建立提交屏障，取消在途模型生成，保留已持久文字和已提交稿件；短提交若已先行进入，先可靠登记结果，不把取消说成撤销保存。随后处理用户输入及相关上下文审核。取消仍可能计费，按G10记录。

若只是讨论且原授权/预算仍有效，回应后可恢复原未完成工作；改方向按新计划决定处理。明确停止、用户关闭或因授权问题暂停，不能因一次闲聊自动恢复。普通输入不改变有效授权epoch，不把旧的可用成果全部作废。

归档推荐“暂停并归档”：停止新工作，完成必要本地状态收尾，保存阶段归属与预算，再登记归档；不依赖等待远端请求自然结束。操作未完成时显示真实状态，失败/重开可核对，不丢任务。恢复归档仅恢复可操作会话，明确继续后才产生新模型调用。已归档历史的只读/Undo保护和32名额规则照旧。

验证出口：生成/本地提交/等待作者时分别插话或归档；跨会话晚到事件归属正确；恢复会话不会自动计费；普通讨论不永久取消原目标。T3、T5随本项一并确认，运行时效果尚待实现和验证。

### G12 旧工程升级与回退：合并原T4

推荐“保留完整副本，验证迁移，再启用新工程格式”。先停止写入并检查脏稿/未决恢复状态，在受控临时副本上迁移；保留并校验升级前的完整工程。新副本验证通过后才作为工作工程使用，旧工程不在迁移过程中被覆盖。数据库副本必须是一致的恢复点，不复制一份仍在变化的主文件就算备份完成。

新工作工程使用旧版入口实际拒绝的工程schema，不能只给新增Stage目录加版本。迁移保留作品与session/message/change/批准回执引用；副本的运行、缓存与lease以物理工程作用域隔离，不能因原身份相同而串用状态。新格式读者明确旧历史和新流式存储如何关联，未知版本拒绝写入，不调用旧v1重置清理新状态。

失败保留原工程并报告停点；新工程启用后如需旧版，只能打开升级前副本。升级后的内容可以通过另行受控流程转移，但本方案不承诺自动向旧版合并新进度，也不增加未经设计的降级写入。升级入口展示这个限制及两份工程的位置。

验证出口：真实旧二进制建立的合成工程、迁移各中断点、空间不足、损坏备份、旧版打开新格式、复制工程同时打开及原工程恢复；原稿/原证据Hash保持可核对。T4随本项一并确认，具体迁移合同及旧版拒绝行为尚待实现和验证。

### G13 流式保存的具体方案

推荐ConversationStore使用“有序追加分段＋持久检查点”，不每0.2～0.5秒重写整个历史JSON。每段含会话/消息/attempt身份、单调序号、长度/完整性信息和有界可见文本；时间与字节双阈值持久化成功后才发布。帧尾不完整时只恢复到最后完整检查点，不能丢弃前面已发布的完整段。

现有session/message身份及默认路径保留兼容入口；升级合同明确旧快照与新增段的读法及唯一权威，不能让旧JSON和段日志各自独立修改同一正文。检查点/归并采用新的不可变代次，完整写入并校验后再原子切换有效清单；崩溃时从仍有效的旧代次恢复。清理仅限已被验证替代、无恢复引用的物理重复段，不删除可见聊天或Undo证据。压缩不在确认关闭时强制等待完成。

UI按已持久位置补齐事件缺口与去重；已保存文字的更正以新事件关联旧片段，不能静默覆写旧记录。数据库/段文件、临时写入和归并都计算配额，满盘前保留恢复余量；实际满盘时停止新增请求，保留已持久内容。

验证出口：短/长历史、连续流、只有末尾一条delta、磁盘慢/满、段尾撕裂、检查点切换中断、UI漏事件和重复事件；长历史的每批写入量不随全部聊天长度线性增长。性能目标以同机基线及实测冻结，T1批量延迟目标不当作网络或审核总延迟保证。

### G14 跨Store恢复与整书定稿验证

推荐先实现故障注入用的最小纵向流程，再接完整创作：一个真实用户输入、一个批准目标、一个Canon效果、一个控制回执、一次重开。随后扩展到多个章节的定稿批次。每个持久边界前后都可强制退出，不能只测试正常成功或网络失败。

| 注入位置 | 必须观察到的恢复结果 |
| --- | --- |
| 作者消息已保存，收件引用未登记 | 本地补登记且只处理一次，不伪造消息 |
| 预算prepared/dispatching前后 | 未发送与可能计费分开；重开不重发旧请求 |
| 意图已保存，Canon未执行 | 核对权限/来源后等待授权继续；不假称已保存 |
| Canon已Committed，控制库未登记 | 关联原回执，不重复修改文件 |
| 批准/事实转确认/下一阶段授权事务中断 | 整组已提交或整组未提交，不能只有部分生效就派发 |
| 定稿若干章后中断或外部修改 | 明确显示批次未完成；核对后只接续未完成成员；所有整书导出入口受同一完成屏障保护 |
| UI事件、保存回执或最终回复丢失 | 从持久Store补齐；不请求模型来猜是否保存 |

数据不变量：已Committed不被后续错误否认；未知外改不强写；每一实际请求可对账；未确认继续前无后台调用；整书输入清单与导出产物证据一致。全部使用隔离合成稿件和loopback，测试通过后再走既有质量门及固定Release验证，不自动使用真实小说或Provider。

### G15 上下文审核专项验收

推荐先固定带人工标注的多轮语料，起始至少200个场景作为工程候选规模；覆盖明确名称、别称、可解析指代、真正歧义、重名、物件转移、插叙、角色谎言/未知秘密、聊天候选、作者手改、跨会话变更、缓存过期、检索失败，以及正式审稿的肯定/否定/引文。每个场景标预期实体、相关源版本、应有或不应有的冲突、允许动作，避免模型自己的回答同时充当标准答案。

| 指标 | 已采纳的初始验收目标（待样本校准，不是已测成绩） |
| --- | --- |
| 明确名称实体召回 | ≥98%，以应识别的实体提及为分母 |
| 别称/可解析指代正确关联 | ≥95%，漏识别也算失败；真正歧义单独统计 |
| 歧义处理 | ≥95%正确澄清或保留未知，不能靠猜测补分 |
| 已知矛盾识别 / 正常变化误报 | 召回≥95%；预设无矛盾样本误报≤5%，两项分开报告 |
| 来源引用支持与版本 | 沿用至少95%要求；缺引用、错版本、不支持断言均失败 |
| 越权写入、跨工程混用、无请求正式审稿 | 受控边界与指定反例零违规，任一违规即失败 |
| 延迟与费用 | 同机/同Provider/同语料比较首段和整轮P50/P95、额外请求与用量；本地检索、持久化、模型等待分别计时 |

上述百分比不代表任意生产输入的可靠性保证；按Provider/model/语料类别分别报告，不能用总平均掩盖指代类失败。固定语料通过后扩展留出样本、20万字完整流程及既有30万/100万字检索范围。离线桩验证Host分支和故障恢复，真实模型识别与创作质量仍由既有受控参与者试用证明，助手不自动运行Live。

正式审稿只在作者明确请求的样本中执行；阶段/全书完成样本必须证明没有偷加审稿调用。既有P95回退超过20%的处理纪律及人工质量评定保留，新增阈值不能替代原质量门。所有未运行/缺证项如实标not_run/unverified。
